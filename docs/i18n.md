# Languages

The dashboard and the desktop app's menu are translated. English and Spanish
ship today. Adding a language means adding translation files; no code needs to
change.

## Choosing a language

- **First run.** Home opens with a "Choose your language" card above the setup
  checklist, with one button per language, each written in its own language.
  The sign-in page has a language menu in its top-right corner.
- **Any time.** The sidebar has a language menu under Settings, and Settings
  has one under Appearance.
- **Default.** Until someone picks one, the dashboard follows the browser's
  language (`es-MX` gives Spanish) and the desktop menu follows the system's.
  Either falls back to English.

The choice is kept in two places:

- The browser remembers it (`localStorage`, key `plughive.locale`), so the
  sign-in page is already in the right language.
- Once signed in, the dashboard also saves it with the daemon, in
  `<home>/preferences.json` (`{"locale": "es"}`), through
  `GET`/`PUT /api/preferences`. Other browsers and the desktop app read it
  from there. When the daemon has a saved language it wins over the
  browser's. When it has none, a choice made on the sign-in page gets saved.

The desktop app checks `preferences.json` every few seconds. A change made in
the dashboard relabels the menu-bar menu, dialogs and notifications without a
restart. The macOS application menu (Edit, Window) changes at the next start.

## What is translated

| Translated | Stays in English |
| --- | --- |
| Every dashboard page, dialog, toast and form label | Tool names, descriptions and schemas that MCP clients see |
| Error messages the dashboard explains in plain words | Raw error text from providers and the daemon, shown as details |
| Dates, numbers, sizes and durations (formatted for the language) | `plughive` command-line output and logs |
| The desktop menu, its dialogs and approval notifications | Restart hints that the client connectors return |

## Adding a language

```bash
pnpm i18n:new fr "Français"
```

The command copies the English files to:

- `web/src/i18n/locales/fr/*.json`, the dashboard. There is one file per area
  (`common.json`, `settings.json`, `jobs.json`, ...), and `_meta.json` holds
  the language's name for itself, as shown in the pickers.
- `app/src-tauri/locales/fr.json`, the desktop menu, dialogs and notifications.

Use a BCP 47 code: `fr`, `de`, `pt-BR`, `zh-Hans`. Then translate the values.

- Leave keys and `{placeholders}` as they are. Their order in the sentence can
  change: `"{count} tokens"` can become `"tokens: {count}"`.
- A key whose value is an object with `one` / `other` (and `zero`, `two`,
  `few`, `many` where the language needs them) is a plural. The form is picked
  with [`Intl.PluralRules`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules)
  for the language, so give each form the language uses. `other` is always
  required.
- A key you have not translated yet can stay in English: missing keys fall
  back to English, so a partial translation is fine to ship.

Check progress:

```bash
pnpm i18n:status fr
```

It lists missing keys, keys English does not have, and values still the same as
English. Units and product names are often the same as English on purpose.
Then run `pnpm test:web` and `cargo test` in `app/src-tauri`. Both check that
every language has exactly the English keys, every plural has `other`, and the
`{placeholders}` match. The web check also makes sure every `t("...")` key the
code uses exists in English.

The new language shows up in every picker on the next build.

## For developers

Dashboard (`web/src/i18n/`):

- `t("file.path.to.key", { name, count })` returns the text in the current
  language. `index.ts` documents the format.
- `chooseLocale(code)` from `i18n/sync.ts` switches language and saves it with
  the daemon. `setLocale` only switches locally.
- `<LanguagePicker variant="compact" | "choices" | "select" />` is the picker:
  a menu with a globe icon, a row of buttons, or a plain form select. Use it
  wherever a language choice should be offered.
- Dates and numbers go through `lib/format.ts`, which follows the current
  language.
- New text goes in the English file for its area first. Add it to the other
  languages too, or leave it to fall back to English.

Desktop app (`app/src-tauri/`):

- `build.rs` compiles in every `locales/*.json`.
- `i18n::tr("menu.open")` and `i18n::trf("client.connected", &[("name", n)])`
  return the text. `i18n::resolve(daemon_home)` picks the language: saved,
  then system (`LC_ALL`, `LC_MESSAGES`, `LANG`, then `AppleLanguages` on
  macOS), then English.
- A new menu item with a fixed label also goes in `Items::relabel`, so it
  follows a language change.
